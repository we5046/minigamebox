# 게임방 관전 및 게임 중 입장 구조 개편 계획서

> 상태: 폐기된 설계안  
> 범위: 마피아, 라이어, 캐치마인드 공통 방 입장 구조  
> 주의: 이 문서는 구현 계획만 다루며, 현재 코드를 변경하지 않는다.

관전 기능은 구현 복잡도와 비밀 정보 노출 위험을 고려해 도입하지 않기로 결정했다.
기존 관전 더미 UI와 설정은 제거하고, 마피아 방 설정에는 `첫날 사망자 유언` 기능을 추가한다.

## 1. 목표

기존에 설정값만 존재하고 실제 동작하지 않던 `spectator_allowed`를 구현한다.

- 모든 게임방의 기본값은 `관전 비허용`으로 유지한다.
- 관전 허용 방은 게임 진행 중에도 신규 사용자가 입장할 수 있다.
- 게임 진행 중 신규 입장자는 기본적으로 `관전자`가 된다.
- 관전자는 게임 플레이어 수, 승패, 점수, 역할 배정에 영향을 주지 않는다.
- 기존 플레이어의 재접속은 관전 허용 여부와 무관하게 지원한다.
- 게임별 비밀 정보와 행동 권한이 관전자에게 노출되지 않도록 서버에서 강제한다.

## 2. 현재 구조와 문제점

### 2.1 현재 공통 구조

- `rooms.spectator_allowed` 필드와 방 설정 UI는 존재한다.
- 방 입장 RPC는 대기 중인 방을 중심으로 설계되어 있다.
- 게임 중 입장은 캐치마인드에만 별도 RPC가 있으며, 입장자를 실제 플레이어로 추가한다.
- 홈 화면의 `관전하기` 버튼은 비활성 상태다.
- 라이어게임 방 설정은 관전을 강제로 비허용 처리한다.
- `room_players`는 실제 플레이어와 관전자를 구분할 필드가 없다.

### 2.2 단순히 `room_players`에 추가할 때의 문제

현재 게임별 권한과 승패 계산은 참가자 테이블을 기준으로 동작한다.

- 마피아: `room_players.role`, `is_alive`를 사용한다.
- 라이어: `liar_match_players`를 기준으로 제시어 조회, 투표, 점수 계산을 수행한다.
- 캐치마인드: `catchmind_players`를 기준으로 출제자 선정, 정답 제출, 점수와 종료 조건을 계산한다.

따라서 게임 중 입장자를 기존 참가자와 동일하게 추가하면 다음 문제가 발생한다.

- 관전자가 역할 또는 제시어를 받는다.
- 관전자가 투표, 정답 제출, 출제자 선정 대상이 된다.
- 관전자 입장과 퇴장이 승패 및 게임 종료 조건에 영향을 준다.
- 관전자가 게임별 비밀 정보를 조회할 수 있다.

### 2.3 마피아 관전자를 단순 사망자로 처리하면 안 되는 이유

마피아의 중간 입장자는 화면상 사망 상태처럼 표현할 수 있지만, 데이터 권한까지 일반 사망자와 동일하게 처리하면 안 된다.

기존 플레이 중 사망한 사용자는 자신의 역할을 이미 알고 있으며, 사망자 채팅이나 일부 게임 기록을 볼 수 있다. 반면 신규 관전자는 게임 시작 당시 참가자가 아니므로 역할, 팀 정보, 밤 행동 정보 등을 볼 수 없어야 한다.

따라서 마피아 관전자는 다음과 같이 처리한다.

- UI 상태: 게임에 참여할 수 없는 관전 상태
- 서버 상태: `사망한 플레이어`가 아닌 별도의 `관전자`
- 역할: 배정하지 않음
- 승패 및 보상: 제외

## 3. 핵심 설계 원칙

### 3.1 방 멤버십과 게임 참가 자격 분리

사용자가 방에 접속해 있다는 사실과 현재 게임의 플레이어라는 사실을 분리한다.

권장 구조:

```text
room_players
  - 현재 방에 접속한 사용자와 접속 상태 관리
  - participation_type: player | spectator

game_spectators
  - 현재 게임을 관전할 권한과 관전 이력 관리
  - game_id, room_id, user_id, joined_at, left_at

게임별 플레이어 테이블
  - 실제 플레이어만 포함
  - liar_match_players
  - catchmind_players
  - 마피아 게임 참가자 스냅샷 또는 기존 플레이어 구조
```

`room_players.participation_type`은 현재 방 화면에서의 신분을 나타내고, `game_spectators`는 특정 게임에 대한 읽기 권한과 감사 기록을 담당한다.

### 3.2 서버가 입장 신분 결정

클라이언트가 자신을 플레이어 또는 관전자로 임의 지정하지 못하게 한다.

서버는 방 상태와 기존 참가 기록을 기준으로 신분을 결정한다.

| 상황 | 입장 결과 |
|---|---|
| 방이 대기 중 | 일반 플레이어로 입장 |
| 게임 중이며 기존 플레이어가 재접속 | 기존 플레이어로 복귀 |
| 게임 중이며 신규 사용자이고 관전 허용 | 관전자로 입장 |
| 게임 중이며 신규 사용자이고 관전 비허용 | 입장 거부 |
| 게임 결과 화면이며 기존 멤버 | 결과 확인 허용 |
| 게임 결과 화면이며 신규 사용자 | 입장 거부 |

### 3.3 관전자는 게임 참가자 테이블에 넣지 않음

관전자는 다음 테이블과 계산에서 제외한다.

- 게임별 플레이어 테이블
- 역할 배정
- 투표 대상과 투표자
- 점수판과 승자 목록
- 최소 인원 및 활성 플레이어 수
- 출제자 선정
- 게임 결과 및 보상 기록

### 3.4 관전자 기본 권한은 읽기 전용

초기 구현에서는 관전자 채팅을 허용하지 않는다.

- 공개 게임 상태 조회: 허용
- 공개 채팅 및 시스템 메시지 조회: 허용
- 게임 행동 RPC 호출: 거부
- 메시지 전송: 거부
- 비밀 정보 조회: 거부

관전자 전용 채팅이 필요해질 경우 별도 채널과 속도 제한을 추가한다.

## 4. 공통 입장 정책

### 4.1 방 설정

공통 설정:

- `spectator_allowed boolean not null default false`
- `max_spectators integer not null default 20`

관전자는 `max_players`를 소비하지 않는다. 다만 무제한 접속으로 인한 Realtime 및 데이터 조회 부하를 막기 위해 별도의 최대 관전자 수를 둔다.

### 4.2 게임 중 입장

게임 중 신규 사용자가 방 입장을 요청하면 다음 순서로 검증한다.

1. 인증 여부 확인
2. 방 존재 여부 확인
3. 비공개 방 비밀번호 확인
4. 기존 게임 플레이어의 재접속인지 확인
5. 신규 사용자라면 `spectator_allowed` 확인
6. 최대 관전자 수 확인
7. `room_players`에 관전자 신분으로 추가
8. `game_spectators`에 현재 게임 관전 기록 추가
9. 게임별 공개 관전 payload 반환

### 4.3 재접속

기존 플레이어의 재접속은 관전 허용 여부와 관계없이 허용한다.

- 기존 게임 참가 기록이 있으면 플레이어 신분을 복구한다.
- 클라이언트가 관전자 입장을 요청해도 기존 플레이어를 관전자로 강등하지 않는다.
- `pending_leave_at`, `connection_status`, `disconnected_at`을 초기화한다.

### 4.4 나가기와 접속 종료

- 관전자 퇴장은 관전 기록과 방 접속 상태만 변경한다.
- 관전자 퇴장은 게임 종료 및 인원 부족 판정을 실행하지 않는다.
- 실제 플레이어 퇴장은 기존 게임별 reconcile 로직을 실행한다.
- 마지막 방 멤버가 나갔을 때만 빈 방 정리 정책을 적용한다.
- 방장 위임 대상은 관전자가 아닌 활성 플레이어로 제한한다.

### 4.5 방 목록과 입장 UI

게임 중 방 표시는 다음과 같이 구분한다.

- 관전 비허용: `게임 진행 중`
- 관전 허용, 여유 있음: `관전 가능`
- 관전자 정원 초과: `관전 인원 마감`
- 기존 플레이어 재접속 대상: `게임으로 복귀`

방 내부에서는 플레이어와 관전자 목록을 분리해 표시한다.

## 5. 게임별 처리 방침

| 항목 | 마피아 | 라이어 | 캐치마인드 |
|---|---|---|---|
| 중간 입장 신분 | 별도 관전자, 화면상 행동 불가 상태 | 별도 관전자 | 별도 관전자 |
| 게임 참가자 테이블 | 추가하지 않음 | `liar_match_players`에 추가하지 않음 | `catchmind_players`에 추가하지 않음 |
| 비밀 정보 | 역할, 팀, 밤 행동, 비공개 채팅 차단 | 제시어와 라이어 정체 차단 | 라운드 정답을 결과 전까지 차단 |
| 공개 정보 | 낮 공개 상태, 공개 채팅, 공개 투표 결과 | 카테고리, 공개 토론, 공개 투표 상태, 결과 | 캔버스, 공개 채팅, 점수, 라운드 상태 |
| 행동 | 채팅, 투표, 능력 사용 불가 | 설명 순서 참여, 채팅, 투표, 추측 불가 | 그림, 정답 제출, 점수 획득 불가 |
| 승패 영향 | 생존자 수와 승패 계산에서 제외 | 점수, 승자, 투표 인원에서 제외 | 출제자, 점수, 활성 인원에서 제외 |
| 퇴장 영향 | 게임 진행에 영향 없음 | 게임 진행에 영향 없음 | 게임 진행에 영향 없음 |

### 5.1 마피아게임

중간 입장자는 게임 플레이 관점에서 행동할 수 없다는 점은 사망 상태와 유사하지만, 일반 사망 플레이어와 권한은 분리한다.

처리 방침:

- 역할을 배정하지 않는다.
- `role = null`, `is_alive = false`만으로 권한을 판정하지 않는다.
- 모든 행동 RPC에서 실제 게임 시작 참가자인지 추가 검증한다.
- 마피아 채팅, 경찰 조사 결과, 의사 행동, 밤 행동 내역을 볼 수 없다.
- 사망자 전용 채팅이 존재한다면 관전자는 접근하지 못한다.
- 공개 낮 채팅과 공개 투표 결과만 조회한다.
- 승리 조건, 생존 인원, 게임 결과 기록에서 제외한다.

필요한 보안 변경:

- `is_alive = false` 조건만으로 비공개 채널 접근을 허용하는 정책 제거
- `is_mafia_game_player(game_id, user_id)`와 `is_game_spectator(game_id, user_id)` 분리
- 관전자용 마피아 payload 추가

### 5.2 라이어게임

라이어게임 관전자는 제시어와 라이어 정체를 알 수 없어야 한다. 관전자를 기존 매치 플레이어에 추가하면 시민 제시어 조회와 투표 참여가 가능해지므로 반드시 분리한다.

처리 방침:

- `liar_match_players`, `liar_scores`에 추가하지 않는다.
- `get_my_liar_state` 호출을 허용하지 않는다.
- 라운드 결과 전에는 제시어와 라이어 ID를 반환하지 않는다.
- 설명 순서, 투표자 수, 재투표 후보, 점수 계산에서 제외한다.
- 공개 토론 내용과 진행 상태는 조회할 수 있다.
- 라운드 결과 단계에서는 공개된 제시어와 라이어 정보를 볼 수 있다.

기존 라이어게임 설정에서 관전을 강제로 끄는 처리는 백엔드 보안과 관전 payload가 완성된 뒤 제거한다.

### 5.3 캐치마인드

관전자는 그림과 공개 채팅을 볼 수 있지만 출제자 또는 정답자가 될 수 없다.

처리 방침:

- `catchmind_players`에 추가하지 않는다.
- 출제자 랜덤 선정 대상에서 제외한다.
- 정답 제출 RPC와 캔버스 저장 RPC를 거부한다.
- 게임 종료 전까지 정답 단어를 반환하지 않는다.
- 점수와 활성 플레이어 수 계산에서 제외한다.
- 관전자 퇴장은 `reconcile_catchmind_match`의 인원 부족 판정에 영향을 주지 않는다.

현재 캐치마인드는 게임 중 신규 사용자를 실제 플레이어로 추가하는 예외가 있다. 이 기능은 관전과 의미가 다르므로 다음처럼 분리한다.

- `spectator_allowed`: 세 게임 공통 읽기 전용 관전 허용 여부
- `late_player_join_allowed`: 캐치마인드 전용 게임 중 플레이어 합류 허용 여부

`late_player_join_allowed`는 별도 제품 정책으로 유지할 수 있으나 기본값은 비허용을 권장한다. 관전 기능 구현 시 기존 캐치마인드 중간 입장 동작을 자동으로 관전으로 바꾸지 말고, 마이그레이션 정책을 명시적으로 결정해야 한다.

## 6. 데이터베이스 변경 구상

### 6.1 `room_players` 확장

예상 필드:

```sql
participation_type text not null default 'player'
  check (participation_type in ('player', 'spectator'))
```

기존 행은 모두 `player`로 마이그레이션한다.

### 6.2 `game_spectators` 추가

예상 구조:

```sql
game_id uuid not null
room_id uuid not null
user_id uuid not null
joined_at timestamptz not null default now()
left_at timestamptz
primary key (game_id, user_id)
```

이 테이블은 다음 용도로 사용한다.

- 특정 게임 관전 권한 확인
- Realtime 구독 권한 확인
- 관전 인원 계산
- 입장 및 퇴장 감사 기록

### 6.3 공통 보조 함수

예상 함수:

- `private.is_room_player(room_id, user_id)`
- `private.is_room_spectator(room_id, user_id)`
- `private.is_game_player(game_id, user_id)`
- `private.is_game_spectator(game_id, user_id)`
- `private.get_room_entry_context(room_id, user_id)`

게임별 함수는 공통 보조 함수와 게임별 실제 참가자 테이블을 함께 검증한다.

## 7. RPC 및 RLS 변경 구상

### 7.1 입장 RPC

권장 방식은 기존 입장 RPC를 서버 판정형으로 확장하는 것이다.

```text
join_room
  waiting -> 플레이어 입장
  playing + 기존 플레이어 -> 재접속
  playing + 신규 사용자 + spectator_allowed -> 관전자 입장
  playing + 신규 사용자 + spectator disallowed -> 거부
```

클라이언트가 `participation_type`을 직접 전달해 권한을 선택하지 않게 한다.

### 7.2 관전자 payload

기존 플레이어 payload를 그대로 재사용하지 않는다. 게임별 관전자용 payload 또는 서버 필터링 계층을 추가한다.

- `get_mafia_spectator_state`
- `get_liar_spectator_state`
- `get_catchmind_spectator_state`

플레이어용 함수에서 필드를 조건부로 제거하는 방식도 가능하지만, 비밀 정보 노출 위험을 줄이기 위해 별도 관전자 payload를 권장한다.

### 7.3 행동 RPC 보호

모든 게임 행동 RPC는 RLS만 믿지 않고 함수 내부에서 실제 플레이어 여부를 확인한다.

- 마피아 능력 사용 및 투표
- 라이어 투표, 추측, 단계 진행
- 캐치마인드 정답 제출, 그림 저장, 단계 진행

관전자는 공개 조회 RPC 외의 호출에서 항상 거부한다.

### 7.4 Realtime

관전자는 공개 테이블만 구독한다.

- 공개 상태 및 공개 메시지: 허용
- 비밀 역할 및 제시어 테이블: 차단
- 게임별 내부 참가자 테이블: 필요한 공개 필드만 별도 payload로 제공

Realtime 이벤트 자체에 비밀 필드가 포함되지 않도록 publication과 RLS를 함께 점검한다.

## 8. 프론트엔드 변경 구상

### 8.1 홈 화면

- 관전 가능한 진행 중 방에 `관전하기` 버튼 활성화
- 기존 플레이어에게는 `게임으로 복귀` 표시
- 관전 비허용 방은 입장 버튼 비활성화
- 캐치마인드의 플레이어 중간 합류가 유지된다면 `게임 참여`와 `관전하기`를 구분

### 8.2 게임방 화면

- 상단에 `관전 중` 상태 표시
- 행동 버튼, 입력창, 투표 UI, 그림 도구 비활성화 또는 미표시
- 플레이어 목록과 관전자 목록 분리
- 관전자에게 비밀 정보 영역을 렌더링하지 않음
- 나가기 버튼과 페이지 이탈 감지는 기존 접속 종료 처리와 연결

클라이언트에서 숨기는 것은 UX를 위한 것이며, 실제 권한 차단은 반드시 서버에서 처리한다.

## 10. 테스트 계획

### 10.1 공통 입장 테스트

- 관전 비허용 진행 중 방에 신규 사용자가 입장할 수 없는지 확인
- 관전 허용 진행 중 방에 신규 사용자가 관전자로 입장하는지 확인
- 기존 플레이어가 관전 비허용 방에도 재접속할 수 있는지 확인
- 비공개 방 관전 입장에도 비밀번호가 필요한지 확인
- 플레이어 정원과 관전자 정원이 별도로 적용되는지 확인

### 10.2 권한 및 정보 노출 테스트

- 관전자가 게임 행동 RPC를 직접 호출해도 거부되는지 확인
- 마피아 역할, 팀 채팅, 밤 행동 정보가 노출되지 않는지 확인
- 라이어 제시어와 라이어 정체가 결과 전까지 노출되지 않는지 확인
- 캐치마인드 정답이 결과 전까지 노출되지 않는지 확인
- Realtime payload에 비밀 필드가 포함되지 않는지 확인

### 10.3 승패 및 종료 테스트

- 관전자가 플레이어 수에 포함되지 않는지 확인
- 관전자 입장과 퇴장이 게임 종료 조건에 영향을 주지 않는지 확인
- 관전자가 점수, 승자, 결과 기록에 포함되지 않는지 확인
- 실제 플레이어 퇴장 시 기존 reconcile 로직이 정상 동작하는지 확인

### 10.4 접속 종료 테스트

- 새로고침과 일시적인 네트워크 끊김 후 신분이 유지되는지 확인
- 브라우저 닫기와 `Alt+F4` 이후 관전자 접속 상태가 정리되는지 확인
- 다중 탭 사용 시 한 탭 종료만으로 사용자가 즉시 퇴장 처리되지 않는지 확인

## 11. 배포 및 마이그레이션 주의사항

- 기존 `room_players` 행은 모두 플레이어로 백필한다.
- 기존 방의 `spectator_allowed`는 `false`로 유지한다.
- 진행 중인 기존 게임에는 관전자 입장을 허용하지 않는다.
- DB 및 RLS 변경을 먼저 배포하고, 관전 UI는 마지막에 활성화한다.
- 캐치마인드 기존 중간 플레이어 합류 동작은 별도 정책 결정 전까지 유지하거나 명시적으로 비활성화한다.
- 오래 남은 진행 중 방과 유령 참가자 데이터 정리 작업을 배포 전 수행한다.

## 12. 결정이 필요한 항목

구현 시작 전에 다음 항목을 확정해야 한다.

1. 관전자 공개 채팅 전송을 영구 비허용할지, 추후 별도 채널로 허용할지
2. 관전자에게 투표 현황을 실시간 공개할지, 투표 종료 후 공개할지
3. 방당 최대 관전자 수 기본값
4. 캐치마인드의 게임 중 실제 플레이어 합류 기능 유지 여부
5. 관전자가 다음 게임 시작 전 로비에서 플레이어로 전환되는 방식
6. 마피아 사망자 채팅과 관전자 채팅을 완전히 분리할지 여부

## 13. 권장 최종 정책

- 세 게임 모두 `spectator_allowed = false`를 기본값으로 사용한다.
- 관전 허용 시 게임 중 신규 입장자는 읽기 전용 관전자로만 입장한다.
- 기존 플레이어의 재접속은 항상 플레이어 복귀로 처리한다.
- 관전자는 일반 사망자나 게임별 플레이어로 모델링하지 않는다.
- 관전자의 게임 중 플레이어 전환은 허용하지 않고, 다음 게임을 위해 로비로 돌아온 뒤에만 가능하게 한다.
- 캐치마인드의 실제 플레이어 중간 합류는 관전 설정과 분리된 별도 옵션으로 관리한다.
- 서버의 게임별 관전자 payload와 권한 검증을 완료하기 전에는 프론트엔드 관전 버튼을 활성화하지 않는다.
